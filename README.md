# Практическая работа: Многопоточная система мониторинга компьютера на Java

**Продолжительность:** 40--50 минут.

**Тема:** многопоточность, асинхронность, `ExecutorService`, `Future`,
`CompletableFuture`, композиция и программирование через интерфейсы.

## 1. Постановка задачи

Необходимо разработать расширяемую систему мониторинга компьютера,
которая собирает информацию об операционной системе и аппаратном
обеспечении.

Система должна уметь получать различные показатели:

-   загрузка процессора;
-   использование оперативной памяти;
-   свободное место на дисках;
-   информация о сетевых интерфейсах.

При этом система не должна быть жёстко привязана к конкретным
показателям. В будущем должна быть возможность добавить монитор
температуры процессора или сетевой активности, не изменяя существующую
инфраструктуру.

Для этого необходимо разработать несколько абстракций:

1.  `Monitor` --- интерфейс отдельного монитора.
2.  `Metrics` --- интерфейс для работы с набором собранных показателей.
3.  `MapMetrics` --- реализация `Metrics` на основе `Map`.
4.  `MonitorDispatcher` --- диспетчер, хранящий список мониторов и
    предоставляющий к ним доступ.

После этого необходимо реализовать два механизма сбора информации:

-   с помощью `ExecutorService` и `Future`;
-   с помощью `CompletableFuture`.

## 2. Подготовка проекта

Создайте Maven-проект.

Добавьте зависимость OSHI:

``` xml
<dependency>
    <groupId>com.github.oshi</groupId>
    <artifactId>oshi-core</artifactId>
    <version>6.9.2</version>
</dependency>
```

Библиотека [OSHI](https://github.com/oshi/oshi) позволяет получать
информацию об аппаратном обеспечении и операционной системе.

Для получения информации о дисках можно использовать стандартный Java
API.

## 3. Проектирование системы

Перед реализацией необходимо создать основные интерфейсы и классы.

### 3.1. Интерфейс Metrics

Создайте интерфейс `Metrics`, представляющий набор собранных
показателей.

Он должен предоставлять следующие методы:

``` java
public interface Metrics {

    Object get(String key);

    <T> T get(String key, Class<T> type);

    boolean contains(String key);

    Set<String> keys();

    Map<String, Object> getValues();
}
```

Назначение методов:

  Метод              Назначение
  ------------------ ---------------------------------------------------
  `get(key)`         Получить значение по ключу
  `get(key, type)`   Получить значение с приведением к указанному типу
  `contains(key)`    Проверить наличие показателя
  `keys()`           Получить набор ключей
  `getValues()`      Получить все показатели

### 3.2. Реализация MapMetrics

Создайте класс `MapMetrics`, реализующий интерфейс `Metrics`.

Внутри класса необходимо использовать `Map<String, Object>` для хранения
показателей.

Например, монитор оперативной памяти может возвращать следующие данные:

``` java
Map<String, Object> values = Map.of(
    "memory.used", 8192L,
    "memory.total", 16384L,
    "memory.available", 8192L
);
```

Реализуйте все методы интерфейса `Metrics`.

**Требования:**

-   Набор показателей должен быть неизменяемым после создания объекта.
-   Нельзя предоставлять внешнему коду возможность изменять внутреннюю
    коллекцию.
-   При запросе значения с неправильным типом необходимо корректно
    обрабатывать ситуацию.

### 3.3. Интерфейс Monitor

Создайте интерфейс `Monitor`, описывающий отдельный источник системной
информации.

``` java
public interface Monitor {

    String getName();

    Metrics collect();
}
```

Каждый монитор должен самостоятельно получать необходимые системные
данные и возвращать объект `Metrics`.

При этом монитор:

-   не должен знать о существовании других мониторов;
-   не должен самостоятельно создавать потоки;
-   не должен использовать `ExecutorService`;
-   не должен зависеть от `CompletableFuture`.

Его единственная задача --- собрать определённый набор показателей.

### 3.4. Реализация мониторов

Создайте три реализации интерфейса `Monitor`:

**CpuMonitor**

Собирает:

-   `cpu.usage` --- загрузка процессора в процентах.

**MemoryMonitor**

Собирает:

-   `memory.used` --- используемая оперативная память;
-   `memory.total` --- общий объём оперативной памяти;
-   `memory.available` --- доступная оперативная память.

**DiskMonitor**

Собирает:

-   `disk.total` --- общий объём диска;
-   `disk.free` --- свободное место;
-   `disk.usable` --- доступное для текущего пользователя место.

Для каждого показателя используйте соответствующие методы OSHI или
стандартного Java API.

Для `DiskMonitor` желательно получить информацию обо всех доступных
дисках, а не только о первом разделе. Для этого можно использовать
`File.listRoots()`.

**Важно:** используйте реальные данные операционной системы. Не
имитируйте получение информации с помощью `Thread.sleep()`.

Исключение --- `CpuMonitor`: для вычисления загрузки процессора
необходимо сравнить два измерения системных счётчиков с определённым
интервалом между ними.

## 4. Создание диспетчера мониторов

Создайте класс `MonitorDispatcher`.

Его задача --- хранить список доступных мониторов и предоставлять к ним
доступ.

Диспетчер не должен самостоятельно собирать информацию или управлять
потоками.

Пример предполагаемого использования:

``` java
MonitorDispatcher dispatcher = new MonitorDispatcher();

dispatcher.register(new CpuMonitor());
dispatcher.register(new MemoryMonitor());
dispatcher.register(new DiskMonitor());

List<Monitor> monitors = dispatcher.getMonitors();
```

**Требования:**

1.  Диспетчер должен хранить коллекцию объектов `Monitor`.
2.  Должна существовать возможность зарегистрировать новый монитор.
3.  Должна существовать возможность получить список зарегистрированных
    мониторов.
4.  Внешний код не должен иметь возможности напрямую изменять внутреннюю
    коллекцию диспетчера.
5.  Желательно предусмотреть защиту от регистрации одного и того же
    экземпляра монитора несколько раз.

Таким образом, для добавления нового источника информации достаточно
зарегистрировать новую реализацию `Monitor`.

## 5. Сбор информации через ExecutorService и Future

Создайте класс `MonitorService`, который будет использовать
`MonitorDispatcher` и `ExecutorService`.

Его задача --- запустить все зарегистрированные мониторы и получить
результаты их работы.

**Требования:**

1.  Создайте `ExecutorService` с пулом из трёх потоков.
2.  Получите список мониторов из диспетчера.
3.  Отправьте каждый монитор на выполнение через `submit()`.
4.  Используйте `Future<Metrics>` для получения результатов.
5.  Соберите все полученные показатели в общий отчёт.
6.  После завершения работы корректно завершите `ExecutorService`.

Для передачи задачи используйте лямбда-выражение или ссылку на метод.

Например:

``` java
Future<Metrics> future =
        executor.submit(monitor::collect);
```

Обратите внимание: `Monitor` не наследуется от `Callable` или
`Runnable`. Задача создаётся непосредственно при отправке метода на
выполнение.

## 6. Сбор информации через CompletableFuture

Теперь реализуйте альтернативный механизм сбора информации с
использованием `CompletableFuture`.

Для этого можно создать отдельный метод в `MonitorService` или отдельный
класс.

**Требования:**

1.  Получите список мониторов из диспетчера.
2.  Запустите каждый монитор через `CompletableFuture.supplyAsync()`.
3.  Используйте собственный `ExecutorService`.
4.  Дождитесь завершения всех операций через
    `CompletableFuture.allOf()`.
5.  Получите результаты всех мониторов.
6.  Сформируйте общий отчёт.

Пример запуска одного монитора:

``` java
CompletableFuture<Metrics> future =
        CompletableFuture.supplyAsync(
                monitor::collect,
                executor
        );
```

Для ожидания завершения всех операций используйте:

``` java
CompletableFuture.allOf(/* список futures */).join();
```

После завершения операций необходимо получить результаты и объединить
их.

### Вопросы

1.  Чем `CompletableFuture` отличается от обычного `Future`?
2.  Почему `allOf()` не возвращает результаты всех переданных задач?
3.  Для чего нужен `supplyAsync()`?
4.  Чем отличается `supplyAsync()` от `runAsync()`?
5.  Обязательно ли `CompletableFuture` использует отдельный поток для
    выполнения задачи?
6.  Чем отличается использование собственного `ExecutorService` от
    стандартного исполнителя `CompletableFuture`?

## 7. Обработка ошибок

Представьте, что один из мониторов не смог получить информацию об
оборудовании. Например, ОС не предоставила доступ к определённому
системному показателю.

Необходимо сделать так, чтобы ошибка одного монитора не приводила к
отказу всей системы.

**Требования:**

1.  Добавьте обработку исключений через `exceptionally()` или
    `handle()`.
2.  Ошибка одного монитора не должна мешать выполнению остальных.
3.  Информация об успешно выполненных операциях должна попасть в отчёт.
4.  Для неудачно выполненных операций необходимо вывести информацию об
    ошибке.

Пример:

``` text
========== SYSTEM REPORT ==========

[CPU Monitor]
cpu.usage: 45.5%

[Memory Monitor]
memory.used: 8192 MB
memory.total: 16384 MB

[Disk Monitor]
ERROR: Unable to collect disk information

===================================
```

## 8. Проверка расширяемости

Добавьте ещё одну реализацию интерфейса `Monitor` на своё усмотрение.

Например:

-   `NetworkMonitor` --- информация о сетевых интерфейсах;
-   `OsMonitor` --- информация об операционной системе;
-   `TemperatureMonitor` --- температура компонентов, если
    поддерживается оборудованием.

Новый монитор должен:

1.  Реализовывать интерфейс `Monitor`.
2.  Возвращать собственный набор `Metrics`.
3.  Регистрироваться через `MonitorDispatcher`.
4.  Автоматически участвовать в сборе информации.

**Главное условие:** для добавления нового монитора нельзя изменять
реализацию `MonitorService`, `Metrics` или `MapMetrics`.
